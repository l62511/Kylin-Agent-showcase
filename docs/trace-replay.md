# Trace、事件与回放

## TL;DR

一次执行由 `trace_id` 贯穿请求、计划、审批、工具调用、回执、审计和评测；事件使用 `event_id + sequence` 排序，断线客户端用 `Last-Event-ID` 恢复，而不是根据文本猜测重复。

## 事件身份

| 字段 | 作用 |
| --- | --- |
| `trace_id` | 关联一次业务请求及其跨协议调用 |
| `request_id` | 幂等和执行账本主键 |
| `event_id` | 单个事件的稳定身份 |
| `sequence` | 同一 trace 内的单调顺序 |
| `event_type` | 普通阶段、审批、终态、错误、取消等分类 |

## 回放路径

1. Gateway 接受 REST/A2A 请求并生成或校验 request fingerprint。
2. Control Plane 落库计划、审批和执行状态，节点回传工具证据。
3. SSE 首次连接读取当前游标；重连携带 `Last-Event-ID`，服务端从持久事件/尾部缓存补发。
4. 回放器按 sequence 重建状态，比较计划、实际工具调用、证据和最终判定。

普通阶段事件允许合并以控制背压，但终态、审批、错误和取消事件必须保留。这样既能降低长任务的事件量，又不会丢失人工接管和安全判定所需的证据。

## 验证边界

展示仓库只发布脱敏结构和历史结果，不发布真实节点地址、完整日志或凭据。运行时回放仍以主项目中的审计链、事件表和 result provenance 为准。
